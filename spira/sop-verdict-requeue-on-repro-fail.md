MATCH: verdict requeues all batch members instead of ejecting the broken one on a red batch
SYMPTOM: A batch fails (red) with the same member across multiple runs; each time, verdict requeues all members rather than ejecting the culprit. Check the verdict log for ejected=0 after a batch failure.
CHECK: Look at the member red in CI, then run a manual repro of the failing suites against that commit. If the suites pass when tested in isolation but verdict still failed to eject, the issue is that testenv-batch.sh's repro pass is not actually testing the branch — it mounts the production checkout (main) and only uses $BR for suite selection and cache key.
FIX: Until sp-2f51e lands (testenv-batch.sh must check out the branch it's given, not just use it for metadata), the workaround is to hand-eject the member via spira/batch.sh (write RED <sha> into landstate with the reason) and re-run the batch. The verdicts' repro logic cannot detect a branch-specific failure because it never checks out the branch.
ESCALATE: None — this is a known harness defect (sp-2f51e) being tracked. The fix requires modifying how testenv-batch.sh sets up the container to check out the branch before running suites.
