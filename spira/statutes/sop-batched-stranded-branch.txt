MATCH: SENDING.*BATCHED.*absent.*open batch|Stranded BATCHED|Stranded IN_DELIVERY|SP_BATCHED_STRANDED=[1-9]|BATCHED.*landstate.*no.*open batch
SYMPTOM: Watchtower escalates "SENDING: BATCHED branch absent from open batch". A branch is BATCHED or IN_DELIVERY on the lifecycle record but its ID is not in any open batch members= line. sending.sh refuses to reap these, so they age indefinitely. IN_DELIVERY variant (sp-941n03, sp-h2m2xw): 21 branches, dropping to 15 within 15 minutes, so some self-resolve as batches close; the stranded set is not static.
CHECK: aeon context lacks SPIRA_RUN/SPIRA_QUEUE_DIR and spira-lc, so the CHECK cannot be run from an aeon; an operator/non-aeon session runs: _id=<id>; spira-lc state $_id; cat $SPIRA_RUN/landstate/$_id; grep "^members=.*$_id:" $SPIRA_QUEUE_DIR/*/open 2>/dev/null || echo "STRANDED: not in any open batch"
FIX: if the branch still points to the BATCHED tip (_tip=$(git -C $SPIRA_REPO rev-parse spira/$_id); _btip=$(awk '{print $2}' $SPIRA_RUN/landstate/$_id); [ "$_tip" = "$_btip" ]), recertify: printf 'CERTIFIED %s %s' "$_tip" "$(date +%s)" > $SPIRA_RUN/landstate/$_id. If the tip moved, escalate. For IN_DELIVERY, first re-read the list on the next tick: branches whose batch has since closed drop out on their own.
ESCALATE: when the tip differs from the BATCHED tip, or when the aeon lacks the env/spira-lc to run the CHECK (the usual case) - leave to operator session; do not loop aeon attempts.
