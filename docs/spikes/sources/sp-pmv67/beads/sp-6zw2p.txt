  test-attribution.sh cases 3 (unreproduced multi-member) and 4a (unreproduced

DESCRIPTION

  ## What is wrong                                                            
                                                                              
  spira/forge.sh already distinguishes the two cases, from the gate's own CI  
  annotations (forge.sh:99-106):                                              
                                                                              
    warning / "flaky suite"      ->  prints  flaky: <suite>          
    error   / "red-twice suite"  ->  prints  red-suite: <suite>      
                                                                              
  spira/gate-retry.sh produces those annotations by re-running the batch's red
  suites SERIALLY and comparing (gate-retry.sh:33-42). red-twice means: re-run
  under a changed condition, red both times. That is the gate stating, in its 
  own                                                                         
  output, that this is not a flake.                                           
                                                                              
  The merge-queue verdict then parses only the red-suite: lines into          
  $red_suites (spira/verdict.sh:117-120) and, when local reproduction finds   
  nothing, calls:                                                             
                                                                              
    _quarantine_suites "$red_suites"                       (:153 and :191)    
    SPIRA_FLAKE_QUARANTINE_AT=1 suites.sh observe-flake     (:78)             
                                                                              
  So the set the gate explicitly classified as NOT flaky is precisely the set 
  that                                                                        
  gets quarantined as flaky — on a single observation, with the configured    
  threshold of 2 overridden at the call site.                                 
                                                                              
  The green path is correct: it forwards the flaky: lines at the default      
  threshold (:320-327). Only the red path inverts the classification.         
                                                                              
  ## Why it is not already fixed                                              
                                                                              
  sp-zmd3u named this as its defect 1 and closed with it explicitly out of    
  scope:                                                                      
  "Defect 1 (red-red suite detection) remains out of scope, requires gate     
  integration". That bead is CLOSED, so nothing carries the remaining work.   
                                                                              
  ## What to do                                                               
                                                                              
  Read the classification that already exists rather than re-deriving it: a   
  suite                                                                       
  arriving on a red-suite: line is ineligible for observe-flake by            
  construction. Remove the SPIRA_FLAKE_QUARANTINE_AT=1 override — one sighting
  is not a threshold, and the configured default is 2.                        
                                                                              
  A regression test must be seen to fail first: feed the attribution path a   
  red-suite: line and require that no quarantine is written.                  
                                                                              
  Found by the sp-pmv67 spike; see docs/spikes/test-identity-lifecycle-and-   
  trust.md.
