DESCRIPTION

  The flake observer counts ANNOTATIONS, not RUNS, so one flaky suite in one  
  CI run                                                                      
  records two or three observations seconds apart and crosses a threshold of 2
  immediately. Every quarantine fired to date rests on this.                  
                                                                              
  ## The evidence                                                             
                                                                              
  $STATE/<suite>.flakeobs ledgers, read 2026-09-17T22:50Z. The window is 7    
  days                                                                        
  (SPIRA_FLAKE_WINDOW=604800) and the threshold is 2                          
  (SPIRA_FLAKE_QUARANTINE_AT):                                                
                                                                              
    test-suites-hygiene.sh          21:50:42, 21:50:43, 21:50:44   3 in 2s    
    test-cockpit-landed.sh          18:00:19, 18:00:21, 18:00:24   3 in 5s    
                                    18:28:17, 18:28:19, 18:28:20   3 in 3s    
    test-cockpit-probe-fault.sh     18:00:15, 18:00:21, 18:00:23   3 in 8s    
                                    18:28:15, 18:28:19, 18:28:20   3 in 5s    
    test-reclaim-slay-branch-guard  15:49:42, 15:49:43, 15:49:44   3 in 2s    
                                    15:51:32, 15:51:33, 15:51:33   3 in 1s    
    test-suites-confirm-red.sh      18:28:14, 18:28:19            2 in 5s     
    test-doctor-embedded.sh         18:00:14, 18:00:22            2 in 8s     
    test-suites-result-files.sh     18:00:12, 18:00:22            2 in 10s    
    test-cockpit-mouse.sh           18:00:17, 18:00:23            2 in 6s     
                                                                              
  Bursts, not a week of independent flakes. Eight suites sit at or over       
  threshold                                                                   
  on data that represents at most one incident each.                          
                                                                              
  ## The mechanism                                                            
                                                                              
  gate-check.sh:125-148 iterates the annotations of a check-run and calls     
  observe-flake once per annotation. GitHub repeats an annotation -- job      
  105386245502 carried the identical "FAIL second obs reaches threshold"      
  message                                                                     
  three times -- so the loop fires N times for one suite in one run.          
                                                                              
  The loop does hold a dedup guard, but it is on the BEAD ("skip if an open   
  bead                                                                        
  titled 'flaky suite: <suite>' exists") and it is demonstrably not holding:  
  the                                                                         
  ledgers above were written with it in place. Whether bead.sh's write is not 
  yet                                                                         
  visible to the bdq list on the next iteration, or the filing failed silently
  under                                                                       
  its 2>/dev/null || true, the observation is recorded either way -- observe- 
  flake                                                                       
  is called after the guard, not protected by it.                             
                                                                              
  ## The unit is wrong                                                        
                                                                              
  An observation means "this suite was red on a parallel run and green on a   
  serial                                                                      
  re-run" -- a property of a RUN. The unit of record must therefore be (suite,
  run_id), deduplicated on that pair, and it must be enforced at the point of 
  recording rather than inferred from a bead query that can fail open.        
                                                                              
  ## Acceptance                                                               
                                                                              
  • observe-flake takes the run id and refuses a duplicate (suite, run) pair. 
  • A suite that feeds two identical annotations from one run and asserts     
  exactly                                                                     
  ONE observation lands -- the positive control being that a genuine second   
  run                                                                         
  still records a second (law-absence-needs-a-positive-control).              
  • Decide what to do with the existing ledgers: every entry was recorded     
  under the                                                                   
  wrong unit, so the counts cannot be repaired by arithmetic. See the note    
  below.                                                                      
                                                                              
  ## Do not fix this by raising the threshold                                 
                                                                              
  law-alerts-must-be-actionable forbids it: the proxy is wrong, not the       
  number.                                                                     
  Raising SPIRA_FLAKE_QUARANTINE_AT would hide burst-counting rather than     
  measure                                                                     
  the property that matters.
